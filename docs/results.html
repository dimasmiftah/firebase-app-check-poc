What was tested

Each browser profile opens /probe/<provider>, which requests an App Check token, calls /api/regular, then sends a limited-use token to /api/sensitive and replays the same token. For reCAPTCHA the page also runs a separate CreateAssessment through /api/diag/recaptcha-score to read the raw risk score.

  • headless-plain: default headless Chrome with automation flags.
  • headless-spoofed: headless, normal user agent, navigator.webdriver hidden, fake plugins and languages.
  • headed-automated: visible Chrome driven by Playwright, default flags.
  • headed-clean: visible Chrome, automation flag removed, webdriver hidden.
  • real-chrome-cdp: a real Chrome started normally with its own persistent profile (no Playwright launch, no spoofing) and driven over the Chrome DevTools Protocol. Site data for localhost is cleared between runs.
    CDP (Chrome DevTools Protocol) is the debugging interface Chrome exposes on a local port. DevTools, Playwright and Puppeteer all use it to inspect and drive a browser. Normally Playwright starts Chrome itself with extra automation flags. Here Chrome is started like a normal user would, and Playwright only attaches to it afterwards, so the browser looks like an ordinary Chrome that a script happens to be controlling.

Direct API cases (no browser)

47 of 47 checks behaved as expected, plus 7 observations that document behavior rather than pass or fail. Green status means as expected, amber means observation, red means unexpected.

Where the tokens come from. reCAPTCHA tokens are real: they were obtained by an automated browser through the Firebase SDK. Automated browsers cannot pass Turnstile, so the Turnstile (custom provider) tokens were minted directly with the Admin SDK createToken() for the Cloudflare app, which is the same call the exchange endpoint makes after Turnstile verification succeeds. The backend sees the same kind of token either way, so these cases test the verification path, not Turnstile itself.

The PoC API has no mode switch: both Firebase apps (reCAPTCHA and Turnstile) are approved at the same time, and the verification layer only looks at the token, not at which provider is enabled. A per-provider switch like the one planned for hermes is not exercised here.

Reading the results

  • The score column lists the raw reCAPTCHA Enterprise score of each run, from a separate CreateAssessment call. App Check performs its own assessment on its own token, so the score shown and the pass or fail of the token exchange are not guaranteed to match.
  • Turnstile error 600010 belongs to Cloudflare's 600* family, documented as "Generic challenge failure" with the guidance "Bot behavior detected". The documentation does not say it is specific to automation. Here it appeared in every automated run and in none of the human runs on the same origin, which supports automation detection but does not prove which signal triggered it. No Firebase call is made when it happens.
  • The reCAPTCHA minimum score threshold in the Firebase Console is 0.5 (as configured by the project owner, not read from the Console). Every reCAPTCHA run in this report scored 0.7 or 0.9 and got a token. No run scored below the threshold, so this data does not test the threshold from below.
  • Human variants: incognito without VPN scored 0.7 (lower than the 0.9 of the normal profile but still passing). With the VPN on, the normal profile still scored 0.9, so the VPN alone did not lower the score in this single run, assuming the VPN changed the egress IP (not verified). The Turnstile widget itself did issue a token with the VPN on: the exchange endpoint was reached with a token and then timed out calling Cloudflare Siteverify, so this run does not show Turnstile rejecting the VPN. The timeout is most likely the API host's network while the VPN was on, which is an inference.
  • On this machine reCAPTCHA did not separate automation from a human. All automated profiles scored 0.9 and received tokens, including 20 of 20 samples each of headless-plain and headless-spoofed. This is a single machine and IP, so it should not be generalized.
  • Turnstile refused every Playwright-launched browser but not a real Chrome driven over CDP. Every run from a browser launched by Playwright got error 600010 (headless and headed, with or without spoofing, in the main run, the 20-sample runs and the parallel runs). The real-chrome-cdp profile, a normally started Chrome with its own profile and no spoofing at all, got a Turnstile token in 3 of 3 runs. So in this PoC Turnstile separates how the browser was launched and driven, not automation as such, and a scripted real browser passes. Which signal Cloudflare uses was not investigated.
  • reCAPTCHA also issued tokens to real-chrome-cdp (score 0.9, 3 of 3), the same as for the spoofed profiles.
  • Design observation: the exchange endpoint calls Siteverify with only the secret and the response token. It does not send the optional remoteip field, so a Turnstile token is not tied to the visitor's IP on our side. Whether Siteverify enforces that field was not tested.
  • Forged, unsigned and tampered tokens are rejected at verification with 401, and the positive controls (an untouched real token, the configured CORS origin) pass, so the negative cases are not passing trivially.
  • Not covered because they need a real human, a different environment, or a config change: reuse of a real Turnstile token (timeout-or-duplicate), Turnstile hostname and action mismatch against a real widget, Cloudflare test keys, a genuinely expired token (needs a 30 minute wait), a threshold sweep in the Firebase Console, other browsers and mobile devices, running from datacenter, residential or mobile IPs, using a token from a different real network, device farms, CAPTCHA solving services, and the human baselines beyond one run each on one machine.

What people say

  • In favor of Turnstile: mostly invisible UX, privacy, free tier, light page weight. One developer reports about 40 ms blocking time versus about 200 ms for reCAPTCHA (single anecdote, not a benchmark). Migration is documented as swapping the script, site key and verification URL (Cloudflare guide).
  • In favor of reCAPTCHA: more mature risk scoring (a 0 to 1 score with Console thresholds) and a longer track record.
  • Concerns about Turnstile: VPN users being challenged or blocked, lock-in to the Cloudflare ecosystem, little public data on effectiveness against sophisticated bots. Cloudflare's docs list disabling a VPN as a troubleshooting step for its generic 600* challenge errors, so VPN friction is plausible.
  • Bypass resistance: the only comparison found is a 2022 study by a competitor (hCaptcha) saying paid bypass services were cheaper and faster against Turnstile than against reCAPTCHA v3. It is almost four years old and from a vendor with a competing product. Blogs say the bypass landscape changes week to week, without measurements (example).

Popularity is not effectiveness. In this PoC, Turnstile refused every browser launched by Playwright while reCAPTCHA let all of them through with a score of 0.9, but a real Chrome driven over CDP got tokens from both, all on one machine and one IP. That does not contradict the adoption numbers, and neither result should be generalized.

Turnstile widgets

A widget is a configuration, not the visible box: it holds a mode (Managed, Non-Interactive or Invisible), a label, a site key and a secret key, plus allowed hostnames (Cloudflare docs). The Free plan allows up to 20 widgets and 10 hostnames per widget. Listing a root domain also allows its subdomains (hostname management). For Indodana the plan is 3 widgets, one each for staging, sandbox and production, so each environment has its own secret key and analytics, and the backend hostname check stays per environment. That is well inside the Free limits. Cloudflare gives no official guidance on one widget versus several, so one widget per environment is a recommendation, not a rule.

What could change the estimate

  • Existing reCAPTCHA Enterprise usage in the organization shares the same free quota and bands, so a real bill depends on total usage, not only this feature. Not known here.
  • Auto token refresh. Firebase documents that App Check creates an assessment each time a regular token refreshes (about twice an hour per active client at a 1 hour TTL). If the app also keeps a regular token alive besides limited-use tokens, assessments exceed one per request.
  • Pricing sources disagree. Google's own billing page gives a flat $8 for the 10,001 to 100,000 band. A third-party page lists about $90 at 100,000 and says the free tier was cut on 2026-04-02, which does not match Google's page. This estimate follows the official page.
  • Quotas at 10x. Firebase says App Check's default per-project quotas are not typically depleted, but the Turnstile path makes about 3,000,000 Firebase or Cloudflare calls per month at 10x. Check the quota page in the Cloud console and ask for an increase before launch if needed.
  • Not priced: compute for the exchange and verification calls on Hermes, any proxy or egress cost, and App Check quota limits for token creation and consumption at 100,000 requests per month. Firebase says default quotas are not typically depleted, but the quota page in the Cloud console should be checked. Replay protection (consume) is also documented as beta.
